# 需求澄清与范围取舍

> **来源**：Jam（FirstProject）项目 2026-09 ~ 10 的实战教训（组 A）；每条标注 `Jam L<编号>`。
> **总纲**：**用户的一句话需求背后常有没写下来的体系；澄清前不要扩大解释，取舍前先查已投入的资产。**
> 用于：会话开场与需求确认（/session-start）、决策记录前的意图确认（/decision-log）。

---

### 1. 先把手上的现象归到"已知成熟方案"，再谈实现（Jam L45）

实例：用户问"如何让某些瓦片上半遮挡、下半不遮挡"，直接给了"把墙拆成上下两个瓦片 + 两层"的首选方案 → 他随后澄清真实需求是「**玩家站在墙后时会被墙遮挡，玩家站在墙前时会遮挡住墙**」，即**随位置自动翻转**，标准答案就是 Godot 原生 **Y 排序（Y-sort）**，**零美术成本、不用拆图**。

判据：

| 现象 | 方案 |
|---|---|
| "随位置翻转" | **Y 排序** |
| "固定半格遮挡" | 拆瓦片 + 分层 |
| "永远在前" | 逐瓦片 `z_index` |

教训：先把手上的现象**归到已知的成熟方案**上（顶视角 2D 的前后遮挡 ＝ Y 排序），再谈具体实现，否则会给出一套更贵、且不是他要的方案。

### 2. 需求里的一词多义先分类，别急着给方案（Jam L19）

实例（**被用户纠正**）：用户说"其实我只是想要雅达利 2600 NTSC 制式的色板"，而回答先给了"GitHub 仓库使用教程"——跑偏了。

判据：**关键词命中 ≠ 需求命中**。先确认他要的是哪一类东西（素材？用法？参数？），再答。

### 3. "不合规范"先问是不是有意为之（Jam L27）

实例：门图 23×8 不符合 GDD 写的"精灵一律取 16 的倍数"，Agent 判定为不合规并建议重画 → 用户两次澄清才把口径定下来（先"门先保持原状，目前用的是带视差的双网格瓦片"，后定案"按 16×16 划分格子，与瓦片尺寸保持一致"）。

教训：**文档里的规范往往是化简写法，用户手里可能有没写下来的体系**。正确动作是"**报告差异 + 问一句是不是有意为之**"，而不是"判定违规 + 给返工建议"。

### 4. 砍范围前先查"会让哪些已投入的东西失效"（Jam L30）

实例（**被用户纠正**）：依据"这是打磨项、时间不够"建议砍掉双网格系统并留到赛后 → 用户当场纠正：「双网格是刚需，目前我所有的地形瓦片都是基于双网格绘制的」。砍掉等于**已投入的地形美术全部作废**。

判据：**做范围取舍前先问一句"这个决定会让哪些已经存在的东西失效"。**

### 5. 用户问"我应该点哪里"时，必须先重读当前仓库（Jam L46）

**不能拿几轮前的读取结果来答。** 实例：项目在一天内从 2 关变成 10 关、`run/main_scene` 换成了 `container.tscn`、TileSet 也被抽成了 `.tres` —— 基于旧读取给的"打开 level3 → 选 Map 节点"已经**指错节点**（各关节点名不同、层数也不同）。

动作：先 `git status` + 读**主场景** + 读目标场景，认出真实节点名 / uid / 层结构，再写步骤。
副产品很值：这次实测顺带捞出了 8 个过期 uid、以及"某目录其实是主场景目录、不是可删残留"这类**只在当前状态才能看到**的结论。

### 6. 协作方要求"先推进"时：把闸门设到后果真正发生的节点（Jam L33）

别硬守"必须先修完才算"。三步：
1. 判断**后果真正在哪个节点发生**（通常远晚于他要求推进的那一步）；
2. 把闸门设到那个节点，并**写进双方都会看的文档**；
3. 留一条**整体回退**路径。

实例：分支夹带第三方素材、对方要求先合 PR → 改判"**合并本身不产生后果，导出上传才会**" → 先零冲突合并、在 ROADMAP 把该 Bug 标成"**上传前硬闸门**"、并记下回退命令 `git revert -m 1 <merge>`。结果：协作没被卡死，风险也没被放过。

### 7. 文档里的条目编号是对外接口（Jam L84）

用户会用**文档里的条目编号**派活：实例 `Ray` 只说「先解决一下 POST_JAM #2」，所指就是 `docs/POST_JAM.md` 第三节表格里的第 2 条。三条要求：
1. **编号必须稳定**——新增条目往后排，不要插队改号，否则他指的和你改的会错位；
2. **状态字段必须实时**——他就是靠状态列判断还欠多少东西；
3. 收到编号指令，**先打开那条读原文**（归属、完成标准、前置依赖都在那一行），别凭记忆作答。

这也是"把收尾清单 / 待办表写进文档"的真正价值。（同见 `shared-references/doc-roles.md` 铁律 5。）
