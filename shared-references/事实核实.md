# 事实核实（下结论之前）

> **来源**：Jam（FirstProject）项目 2026-09 ~ 10 的 88 条实战教训（组 A）；每条标注 `Jam L<编号>`。
> **总纲**：**关键前提一律当场验证（常常只是一条命令的事），不要用"看起来像"替代证据。**
> 用于：会话开场的一致性核对（/session-start）、收尾的事实分拣（/daily-wrap）、提交审查（/commit）、以及任何"要不要相信一份汇报/一条提交信息"的场合。

---

### 1. 自评不可靠，只问可验证的陈述（Jam L20）

评估协作者 / 交付方的技术水平时，**别问"你什么水平"**（自评不可靠，有人把"跟教程跑通"当成"会做"），要问：
- "你做过的最完整的东西是什么？"
- "这几件具体的事，哪几件你不查资料就能做？"

前者得到可验证的陈述，后者直接对上验收线——拿到就能判断排期该排多大、范围要不要砍。
口诀：**教程产物只证明"能跟上"，不证明"能独立做"。**

### 2. 跨角色接口名先定死再开工（Jam L24）

多人分头写代码前，必须先把**方法名、信号名、节点名、资源路径**定死并写进文档。不一致不会报错，只会静默失效。

实例：怪物调用 `body.has_method("take_scare")` → `body.take_scare()`，而玩家脚本定义的方法叫 `take_damage()` → `has_method` 永远返回 false，怪物碰到玩家不扣命、无敌也不触发，整条受伤链路空转到有人逐行读代码才发现。

判据：**凡是"跨角色调用"的东西，名字不确定就不要开工。**

### 3. 审查提交必须单独审计新增的二进制素材来源（Jam L25）

写代码的人常顺手拿教程或网图填洞。二进制文件在 `git diff --stat` 里只有一行 `Bin`，极易划过去。

判据：**看到新增 `*.png / *.wav / *.ogg / *.ttf` 就该当场问来源。** 实例：PR 带进一张作者自己在提交信息里承认来自"未入库第三方教程素材"的光照贴图（只把路径改到已提交的副本），直接撞上版权规则。

### 4. 改 / 删文件前先查"谁在引用它"（Jam L26）

尤其**工程配置里的入口引用**：删文件前 grep 全仓 + 检查 `project.godot` 的 `run/main_scene`（Godot）/ `package.json`（Node）这类入口配置；发现被引用就先补引用再合并。

实例：合并"只上传一张瓦片"的分支时，该分支同时删掉了 `dev/text_playground.tscn`，而 `project.godot` 的 `run/main_scene` 正指向它的 uid → 照单合并会让 main 一打开工程就报悬空引用、跑不起来。

顺带一条：**验证用的临时脚手架要么显式标注"可丢弃"，要么用完立刻删**——它在无人注意时很容易变成正式入口（那个测试场景从 09-23 起一直当着 main 的主场景）。

### 5. 改名 / 移动文件要连带处理派生文件与所有引用（Jam L28）

- Godot 的 `X.png.import` 里写死了 `source_file="res://…/X.png"`，只改 PNG 名字会留下**悬空 `.import`**（指向不存在的源），打开工程就报源文件缺失。
- **git 的改名识别帮不上忙**——它让合并显得"零冲突"，把问题藏起来。
- 判据：出现"有 `.import` 却没有对应源图"或反过来"有 PNG 却缺 `.import`"，就是漏了。
- 补（改名撞上修改）：**`modify/delete` 冲突用默认解法会丢改动**。实例：`scenes/levels/leve1/` 改名 `level1/`，另一侧还在往旧文件里加碰撞层设置 → 合并报 `CONFLICT (modify/delete)` 并**把旧文件版本留在树里**：既让拼错的旧目录复活，又让那几行修正进不了新场景。**处置：改名前双方先同步；撞上时接受改名（保留新路径）并手工把旧文件上的改动移植进新文件 —— 不要 `--ours/--theirs` 一刀切。**

### 6. 判断第三方仓库 / 插件能不能用，核四件事（Jam L29）

别被仓库名和 star 骗了：
1. **它到底是不是插件** —— 有没有 `addons/` + `plugin.cfg`（GDScript）或 `*.gdextension`；很多名为"xx-system-for-godot"的仓库其实只是**示例工程**，只能照思路自己移植；
2. **语言与工程是否一致** —— 看它 `project.godot` 的 `config/features` 有没有 `"C#"`，有就要求 .NET / Mono 版编辑器；
3. **它声明的引擎版本**（同样是 `config/features`，通常落后几个大版本）与**最后更新时间**；
4. **许可证**（MIT 也要求署名）。

结论：**先核实事实，再回答"支不支持"。**

### 7. 权限 / 平台边界：先探针验证，再写成结论（Jam L80）

实例：断言"旧总表归旧租户应用所有、跨租户读不到、必须在新租户重建"，并据此写进两处文档 → 对方开好权限后实测**同一张表直接可读写**（`code=0`），推断被推翻，文档返工更正。

做法：
1. 文档里**区分标注「实测」与「推断」**；
2. 一条 `curl` / 一次工具调用能验证的事，别用推理代替；
3. 报"结论"前先问自己"这条我验过没有"。

### 8. 收到"某人给你发了任务"而自己无记录时：先穷尽核查（Jam L76）

**绝不要凭线索猜着执行。** 核查顺序：
1. `team_inbox` / `team_status`（未读与决策队列）；
2. 工作区 `.dsh/team/log.jsonl` 与 `decisions.md`；
3. 外部平台的任务表 / 决策表；
4. 近若干小时被改动的**全部**文件（不限扩展名）。

核查完再**反向请求重发**（写明要带：要登记什么 / 依据路径或提交号 / 完成标准）。

⚠️ 最大的坑：**记忆系统的关键词命中会送来一条"看起来很像"的旧记忆**——"登记"二字命中了"把项目路径登记进 git `safe.directory`"那条，差点去改 git 配置，实际去查发现**早就登记过了**。判据：**关键前提一律当场验证（一条命令的事），不要用"关键词像"替代证据。**

### 9. "未完成 / 待确认"清单必须逐条实测，不能照抄（Jam L61）

并行的人（或另一个窗口）随时会把它做掉，几小时前写的待办就会变成假警报。

实例：待办里"某处大小写问题（上传硬阻碍）"其实**早已修好**；而"8 处过期 uid"**确实仍未清**——一条假、一条真，只有 grep 过才知道。

做法：对每条"未修 / 待确认"跑一次**最便宜的事实检查**（grep 明文、看文件是否存在、看引用），再决定保留还是划掉。

### 10. 下结论前先确认"基准"是从哪来的（Jam L73 + L74）

实例：把用户新画的血条图（56×14）判成"零引用的废弃文件"，又拿脚本里 `heart_frame_size` 的**默认导出值 8×8** 当基准推算出"尺寸不对、得改成 56×16"——**两个结论都错**：那正是他刚画好的图，而且他用的是 **7×7 一格**（`8 列 × 7 = 56`、`2 排 × 7 = 14`，严丝合缝）。

**正确顺序：默认值、印象、旧读取都不算基准。**
- 判定素材尺寸前，先去 `SpriteFrames` / 图集资源里看每帧 `AtlasTexture` 的真实 `region`，用实际 region 反推网格；
- 说"某文件零引用"之前**先 grep 全仓**，别拿"我在主场景里没看到"当依据。

### 11. 文档里手写的"剩余 X 小时"会自动过期（Jam L39）

带硬截止的项目里，**文档上的过期数字比没有数字更危险**（三处派生数字一起过期是常态）。

做法：每次**会话开场按当前时刻重算并原地改掉**（含各处派生数字），不能只在心里算。
