# 协作与交付（多会话 · 提交 · 交付验收）

> **来源**：Jam（FirstProject）项目 2026-09 ~ 10 的 88 条实战教训中筛出的项目管理方法论（组 A）。每条末尾标注原始编号 `Jam L<编号>`，便于回溯原文。
> **适用**：单人开发者 + 多个 AI 会话 / 协作方**共用同一工作区**；以及任何"要交到外部平台"的交付物。

---

## 一、多窗口 / 多会话协作

### 1. 并发写文档：写前重读、写完回读（Jam L11）

同一工作区**长期存在并发会话**（多个窗口同时改文档并提交）时，有三种表现：

① `edit` 报 "file changed since read"；② 自己的改动看似已被提交（实际是别人提的）；③ ⚠️ **最危险：自己的追加被并发窗口的保存整个覆盖、不留任何痕迹**。

规则：
- 改文档前先 `git log --oneline -5` + `git status` 核对现状；**别盲目重写整份文件**（用 edit 局部改，不用 write 覆盖）。
- **写前重读、写完立刻回读核对**——回读是唯一能发现"被覆盖"的手段。
- 发现同一份文档正被并发写 → **主动提醒用户只留一个窗口写文档**。
- 重要结论**别只留在文档里**，同步落记忆 / 其它载体。

### 2. 共享工作区的提交纪律：只 add 自己改过的文件（Jam L31）

用户 / 其他人**在同一工作区开着编辑器干活**时：
- 提交前必须 `git status` 看清范围，**只 add 自己改过的文件，绝不用 `git add -A`**。
- 反面实例：`git add -A` 把用户未提交的美术文件与练手目录一起提交并推送，其中部分按项目约定本不该进 main。
- **已推送的历史不强改**（禁 force push）：当场说明 + 提议后续修正，比偷偷回滚诚实。

### 3. 一次合并只在一个工具里做（Jam L44）

同一个合并**不要同时在 GUI（GitHub Desktop 等）与命令行两边做**——GUI 的冲突界面不会自动感知命令行已解决：
- 别点 GUI 的"继续合并 / Resolve conflicts"（会再发起一次合并、又生成冲突标记）；
- 让它刷新：`Repository → Fetch origin` → 切一次分支再切回 → 仍不行就重启 GUI（冲突视图只在启动时读盘）；
- 约定：**要么全在 GUI 做，要么全交命令行**。

### 4. 编辑器占着文件句柄时的合并：用 plumbing，不切分支（Jam L56）

切分支会重写整个工作区，撞上被占用的文件就报 `unable to unlink '…': Invalid argument` / `Merge with strategy ort failed`——合并做不成还把状态搞乱。做法（**完全不碰工作区**）：

```bash
tree=$(git rev-parse <分支>^{tree})
git commit-tree $tree -p main -p <分支> -m "Merge …"
git update-ref refs/heads/main <新提交>
git push origin main
```

两个前提先验：① `git merge-base --is-ancestor` 确认分支关系；② 合并后的 tree 与源分支 tree **完全相同**（`git rev-parse main^{tree}` 对得上）。

### 5. 冲突先看冲突区有多大（Jam L57）

- 冲突标记只有几行 → 其余部分已**自动合并成功**，别当成"整份文件要重做"。
- 三个判据：
  1. 冲突常是"**两边在同一位置各加了一行**" → **两行都留**，不是二选一；
  2. 选边前检查**被引用名是否还存在**（选中指向已改名父节点的那版会直接把场景改坏）；
  3. 保留哪边看**谁是最新意图**（`git log` 时间 + 该文件归属人）。
- ⚠️ 用脚本改这类文件会带入 CRLF，与 `text eol=lf` 的 `.gitattributes` 冲突 → 改完 `git checkout -- <文件>` 还原换行并确认 `git status` 干净。

### 6. 网络受限时先问"有没有新东西"，别急着 fetch（Jam L23）

确认远端有没有新提交用 `git ls-remote origin`（轻、快，只列引用）；`git fetch` 要拉对象，可能挂起乃至超时。**先 ls-remote 比对引用，确认真有变化再决定 fetch。**

### 7. AI 的操作边界：只读排查 / 工程操作 / 生成内容（Jam L40）

- **只读排查**：给根因 + 编辑器操作步骤 + 官方文档指路 + 落 devlog，**不碰场景与资源**；不给可复制的代码块。
- **工程操作**（AI 可以代跑）：抽 `.tres`、设 Inspector 字段、改 `export_presets.cfg` 的导出入口、跑 `--headless --export-release`、把产物打成上传 zip。
- **红线**：代码与美术资源（"生成游戏内容"）；以及**别人名下的场景**（按约定先打招呼，或把资源与模板准备好让对方落）。
- 属外部 / 主观的验收必须交给人：**"能不能玩"要人在真机浏览器里验**；AI 只能验"页面是否对外可见"这类客观事实。
- 细则：见 `shared-references/doc-roles.md` 与项目 `PROJECT_INDEX.md` 的职责约定。

## 二、提交历史与事实核实

### 8. 提交信息不等于事实（Jam L36）

关键改动（尤其工程配置、单行字段）**必须 `git show <commit> -- <path>` 核实真实 diff**，别信 commit message。

实例：提交信息写"主场景改 Start"，真实改动只是加了一行指向另一个场景的 `run/main_scene` uid —— 只看信息会把"入口到底是谁"判断错。同理，多人协作里"我改了 X"的汇报要按 diff 核对。

### 9. `git diff --name-status` 里的 `R`（改名）条目必须核对两端（Jam L67）

git 的改名识别会把"某文件被删 + 别处新增一个内容相同的文件"伪装成一次干净改名，于是"**某个目录丢了文件**"这种结构性事故在 diff 里只显示一行 `R100`。

实例：`R100 scenes/levels/level2/map.tscn → assets/sprite/player/map.tscn` —— 真相是**关卡地图被拖进了精灵素材目录**，且引用路径被一并改错（能跑，但位置错、迟早出事）。

判据：**改名的两端路径在语义上不搭（场景文件跑到素材目录）＝ 先怀疑误操作**；改名前后的两端路径都要念一遍。

## 三、交付与验收

### 10. 交付链路提前用占位跑通，不能排在最后（Jam L32）

"能不能交上去"这个问题不能悬到最后一天：入口文件名不对、站点拒收都会让剩余时间不够修。

做法：**产出第一版能跑的包时就传一次占位版**，把"上传 → 可玩"整条路先验通；此后每次重传只是覆盖。同理适用于发版、部署、提交表单。

### 11. 完成标准必须是"在收件方的名单里能看到它"（Jam L77）

"包上传成功 / 页面公开" **≠** "已提交"。**验证必须从收件方视角做**（匿名打开收件方页面，确认自己的条目在其中）。

实例：包已上传、itch 页面已公开、匿名访问 HTTP 200，**却漏点 `Submit to jam`** —— 主办方页面显示"提交已关闭，投票进行中"，43 个参赛条目里没有它（最后靠联系主办方补建，占用对方时间与人情）。

三条做法：
1. "提交"这个动作**指派到具体人 + 具体时间点**；
2. 截止前留一次**提交后复核**（去收件方名单确认条目存在）；
3. **上传入口与提交入口往往不在同一页**（itch：游戏页上传 ≠ Jam 页 Submit），别假设"传完就算参赛"。

### 12. 匿名抓取是复核平台交付状态的最优手段（Jam L83 / L58）

用**匿名 HTTP 请求**抓收件方页面找客观证据，取价比登录后台高得多，且可复现、能留证：
- 页面内嵌 JSON 里常直接带着条目对象（条目 id、贡献者列表、`rating_count`、`created_at`）；
- **时区反推**：拿页面里已知的时间点（如 `end_date` = 确知的 UTC 截止时刻）反推该页时间戳的时区，据此证明"条目创建时间晚于截止"。

⚠️ **边界必须说清**：它能验**可见性**（草稿页对未登录访客返回 404 = 未公开），**验不了可玩性**（wasm 加载、WebGL 渲染、键盘焦点只有人在真机浏览器里能确认）。别把 200/404 说成"游戏没问题"。

### 13. 闸门解除只凭"引用归零"，不凭提交信息（Jam L66）

别人说"那个风险已经清掉了"时，逐项验证：
1. 对每个被删文件名 / 目录跑 `git grep -l -F "<名字>" <ref>` —— **零命中才算干净**；
2. 查**悬空 `.import`**（有 `.import` 没源图，或有图没 `.import`）；
3. 查**入口配置**（`project.godot` 的 `run/main_scene`、autoload 是否还指向被删文件）；
4. 查声称替换上去的自研素材是否真的存在且被引用。

判据：**闸门解除意味着可以公开，误判的代价是版权事故 —— 所以只凭引用归零，不凭提交信息。**

### 14. 让有"黑历史"的仓库安全公开：清历史 + 另建新仓库（Jam L78）

**不要**改原仓库可见性、也**不要** force push 原仓库。正确做法：

1. 完整镜像备份：`git clone --mirror . SOURCE/repo-backup.git`；
2. 在**工作副本**里跑 `python -m git_filter_repo --path-glob '<要删的路径**>' --invert-paths --force`（重写全部 refs、保留时间戳与作者，只删文件；纯删除后变空的提交一并剪掉）；
3. 校验两条：目标路径在 `--all` 历史里 **0 命中** + `HEAD^{tree}` 与原仓库**逐字节相同**；
4. 用 GitHub API 建**新公开仓库**（`POST /user/repos`）→ `git push -u origin main --tags`；
5. **匿名 `git clone --mirror` 把公开仓库拉下来再搜一遍**才算验完。

坑：GitHub API `POST /user/repos` 的请求体**含非 ASCII（中文 / em-dash）会返回 400** → 改用纯 ASCII 最小请求体。

### 15. 破坏性数据操作：先在副本上跑，再动真文件（Jam L81 + L82）

- **"改坏了修不回来"的文件，先复制一份跑同一段代码并校验**（帧数不变 / 末帧仍能解压 / 后续帧字节完全未变 / 原文件长度未动），通过后才动真文件。
- 需要用户配合的多步操作（停服务 → 改数据 → 移目录 → 起服务），**收敛成一条命令的自检 + 自备份脚本**，别让用户当流程协调器（"停服务 / 起服务"这两步最容易把他卡住）。
- 判据：交给用户的应是**一条命令**，不是一份操作手册。

### 16. 给别人的命令，按他的环境写并实跑验证（Jam L87 + L88）

- 先确认那个程序 / 解释器**在他的机器上真的存在**（`Get-Command <名字>` / `which`），别照抄自己环境的写法。
- 交付前按**他会用的那个 shell 的语法**逐字跑一次最轻路径（如不带参数的预检），确认它启动、输出可读、该失败时退出码正确。
- 说明里**同时给出等价的手工写法**，别只给一条命令。
- 实例教训：调用写成 `pwsh -File …`（对方机器只有 Windows PowerShell 5.1）→ `CommandNotFoundException`；改完又漏了 `.\` 前缀（PowerShell 不从当前目录加载命令）——两次都是**照自己的习惯写、而不是照他的环境写**，且都要等他撞了报错才知道。
- 同类：**"能起来"本身也是必须验证的事实**。
