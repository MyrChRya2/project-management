# /bug-track — Bug 登记与跟踪

目标：**每个 bug 有据可查（可复现、有优先级、状态可追踪），修复不遗漏、不重复踩**。

## 流程

```
[用户：发现 bug / 新增 bug + 描述]
   ↓
[Phase 1: 复述确认] 现象 + 触发条件，必要时追问复现步骤/是否稳定复现
   ↓
[Phase 2: 登记] 分配 ID（B1、B2…按序），写入：
   ├─ 当日 devlog → Bug 报告区块（描述/复现/推测原因/优先级）
   └─ ROADMAP → 「已知 Bug 跟踪」表（ID/描述/优先级/状态）
   ↓
[Phase 3: 提交] 文档提交推送
   ↓
[修复后]
   ├─ 更新 ROADMAP 跟踪表：状态 → ✅ 已修复（附修复提交/日期）
   ├─ devlog 补记：根因 + 修复方式
   └─ 关联任务勾选（如该 bug 阻塞某里程碑）
```

## 优先级约定

| 优先级 | 含义 | 状态标记 |
|--------|------|---------|
| P0 | 阻塞核心功能/手感，需立即修 | 🔴 待修复 |
| P1 | 明显缺陷，优化/里程碑前修 | 🟡 待修复 |
| P2 | 偶发/低影响，可搁置 | ⚪ 搁置 |
| P3 / — | 观察中，未确认 | 👁 观察 |

## 规则

- **描述必须可复现**：现象 + 触发条件 + （尽量）复现步骤；不可复现的标"偶发/待观察"。
- **推测原因写进 devlog 但不进跟踪表**：跟踪表只放事实；推测放 devlog 便于修复时定位。
- **修复要记根因**：修完在 devlog 记"为什么坏、怎么修的"，教训沉淀进 DEBUG_NOTES 类知识库。
- **"已修复 / 风险已清除"只凭实测，不凭提交信息**：跑一遍验证、或对相关引用跑 `git grep -l -F "<名字>"` 确认**零命中**，再改状态（`协作与交付.md` §13，Jam L66）。
- 批量报告（多个 bug 一起说）→ 逐条分配 ID 登记，不要合并成一条。
- **ID 只往后排、不改号**：用户会拿 ID 派活；改号会让他指的和你改的错位（`需求与范围.md` §7）。
