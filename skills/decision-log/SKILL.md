# /decision-log — 决策记录与同步

目标：**每个方向性决策都有据可查，且文档之间不自相矛盾**。

## 什么是"值得记录"的决策

- 新增/放弃/归类某个功能（如"放弃 wall_climb""slide 归到 M2"）
- 重构方向选择（如"倾向方案 A，待实施"）
- 范围/优先级调整（如"里程碑拆分""延后 X"）
- 涉及文档职责边界的变更（如"新增日志模板流程"）

纯参数微调、普通 bug 修复 → 记入 devlog 完成内容即可，不必走决策流程。

## 流程

```
[用户：记录决策 + 内容]
   ↓
[Phase 1: 确认意图] 复述决策 + 理由，确认理解一致
   ↓
[Phase 2: 写 devlog] 追加到当日日志（决策与理由区块），无当日日志则新建
   ↓
[Phase 3: 同步]
   ├─ ROADMAP → 决策记录区追加条目；受影响任务勾选/重写/标注
   ├─ GDD → 待决策清单勾掉已决项；设计章节如有变更同步
   └─ 索引 → 涉及路径/结构变更时通知 /index-sync
   ↓
[Phase 4: 提交] 文档改动提交推送
```

## 决策记录格式（ROADMAP 文末）

```
> **决策记录：**
> - YYYY-MM-DD — {{决策内容}}（{{一句话理由}}）。
```

## 规则

- **先确认再落盘**：方向性决策影响后续所有工作，复述确认后再写。
- devlog 是流水账（当时当刻），ROADMAP/GDD 是状态（当前生效）——两者都要更新，缺一不可。
- 决策记录只追加，不删改历史条目；被推翻的决策用"新条目覆盖"，git 历史是档案。
- **范围取舍先查"会让哪些已投入的东西失效"**：砍功能/砍打磨项之前问一句"这个决定会让哪些已经存在的东西（美术、流程、已写代码）作废"（`需求与范围.md` §4，Jam L30 被用户纠正过）。
- **协作方要求"先推进"时不要硬卡**：判断后果真正发生的节点，把闸门设到那里并写进双方都看的文档，同时留一条整体回退路径（`需求与范围.md` §6，Jam L33）。
- 记录用户原话时**逐字保留措辞**——原话里含他的潜在逻辑，转述会丢信息。
